# GoodQueue Frontend

Frontend для будущей демонстрации механики очереди на покупку ограниченного товара.

Сейчас проект находится на стадии bootstrap: настроены приложение, маршрутизация и
общая инфраструктура, но предметные пользовательские сценарии ещё не реализованы.

## Текущее состояние

Уже реализовано:

- CSR-приложение на React 19, TypeScript и Vite;
- `BrowserRouter` и каркас маршрутов;
- общий layout на Mantine `AppShell`;
- тема Mantine, системные уведомления и индикатор сетевой активности;
- единый `QueryClient` и React Query Devtools в development-режиме;
- общие схемы валидации непустой строки и UUID;
- базовый HTTP-клиент в `src/shared/api`;
- конфигурация Jest, React Testing Library, ESLint, Steiger и Prettier;
- пустые route-компоненты для запланированных экранов.

Пока не реализовано:

- загрузка и отображение каталога и карточки товара;
- выбор демонстрационного пользователя;
- предметные `entities`, `features` и `widgets`;
- предметные API-модули, DTO и схемы ответов backend;
- вход в очередь, polling состояния и отмена ожидания;
- приглашение, резерв, checkout, таймеры и результат покупки;
- рекомендации альтернативных товаров;
- компонент `PurchaseQueueFlow` или другой готовый к встраиванию виджет.

## Стек

- React 19 и TypeScript;
- Vite;
- React Router;
- TanStack Query и React Query Devtools;
- Mantine;
- Zod;
- Feature-Sliced Design;
- Jest и React Testing Library;
- ESLint, Steiger и Prettier.

## Архитектура

Исходный код организован по Feature-Sliced Design:

- `src/app` — композиция приложения, провайдеры, маршрутизация, тема и layout;
- `src/pages` — route-компоненты экранов;
- `src/shared` — общая инфраструктура без предметной логики.

Слои `entities`, `features` и `widgets` будут добавляться только вместе с
соответствующей предметной логикой. Предметные API-функции и DTO также должны
располагаться рядом с реализующими их сущностями и сценариями, а не в `shared/api`.

## Реализованная инфраструктура

### Провайдеры приложения

Приложение обёрнуто в:

- `QueryClientProvider` для серверного состояния;
- `MantineProvider` с общей темой;
- `BrowserRouter` для клиентской маршрутизации.

Системные уведомления отображаются в правом верхнем углу, не более трёх
одновременно. Индикатор навигации реагирует на активные запросы и мутации TanStack
Query. React Query Devtools подключаются только в development-режиме.

Для запросов заданы базовые настройки:

- `staleTime` — 30 секунд;
- повтор неуспешного запроса — один раз;
- повторный запрос при возврате фокуса на окно отключён.

### Маршрутизация

Каркас приложения содержит маршруты:

| Маршрут                            | Route-компонент   |
| ---------------------------------- | ----------------- |
| `/`                                | `HomePage`        |
| `/products/:productId`             | `ProductPage`     |
| `/products/:productId/queue`       | `QueuePage`       |
| `/products/:productId/reservation` | `ReservationPage` |
| `/products/:productId/checkout`    | `CheckoutPage`    |
| `/products/:productId/result`      | `ResultPage`      |
| `*`                                | `NotFoundPage`    |

Эти route-компоненты пока являются пустыми заглушками и не отображают предметный UI.

### Shared API

`src/shared/api` содержит только общую инфраструктуру взаимодействия с backend:

- `apiClient<ResponseData>(path, init?)` — типизированная обёртка над `fetch`;
- base URL из `VITE_API_URL`;
- разбор JSON, текстовых и пустых ответов;
- `ApiError` для неуспешных HTTP-ответов со свойствами `status`, `statusText` и
  `data`.

Публичные экспорты доступны через `src/shared/api/index.ts`:

```ts
import { apiClient, ApiError } from '@/shared/api';
```

Клиент принимает стандартный `RequestInit`; заголовки и тело конкретного запроса
задаёт вызывающий предметный модуль. Ошибки сети, при которых HTTP-ответ не был
получен, остаются исходными ошибками `fetch`.

### Общая валидация

`src/shared/lib/validation` экспортирует схемы непустой строки и UUID. Предметные
схемы будут размещаться ближе к соответствующим `entities` и `features`, используя
общие схемы как строительные блоки.

## Локальная конфигурация

Frontend использует `VITE_API_URL` как base URL backend. Шаблон настройки находится
в `.env.example`:

```env
VITE_API_URL=http://localhost:8080
```

Перед локальным запуском создайте `frontend/.env` из шаблона.

PowerShell:

```powershell
Copy-Item .env.example .env
```

Bash:

```bash
cp .env.example .env
```

Локальные адреса по умолчанию:

- frontend — <http://localhost:5173>;
- backend — <http://localhost:8080>;
- Swagger UI backend — <http://localhost:8080/docs>.

Backend должен разрешать CORS для origin frontend. Настройка и запуск backend
описаны в корневом README проекта.

## Локальный запуск

Требования:

- Node.js `24.19.0`;
- npm;
- доступный backend на адресе из `VITE_API_URL` для будущих предметных запросов.

Из директории `frontend`:

```bash
npm ci
npm run dev
```

Vite запустит development-сервер на <http://localhost:5173>.

## Проверки и тестирование

Основные проверки:

```bash
npm run typecheck
npm run lint
npm run steiger
npm run format:check
npm test
```

Дополнительные команды:

| Команда                 | Назначение                                       |
| ----------------------- | ------------------------------------------------ |
| `npm run test:watch`    | Jest в watch-режиме                              |
| `npm run test:coverage` | тесты с отчётом о покрытии                       |
| `npm run lint:fix`      | автоматическое исправление доступных lint-ошибок |
| `npm run format`        | форматирование проекта                           |

Текущие тесты покрывают bootstrap приложения, провайдеры, индикатор активности,
общую валидацию и HTTP-клиент. Предметные сценарии будут покрываться по мере их
реализации. Полная конкурентная логика очереди остаётся ответственностью backend и
его тестов.

## Production-сборка

Проверка типов и production-сборка выполняются одной командой:

```bash
npm run build
```

Результат создаётся в `frontend/dist`.

Для локального просмотра уже собранного приложения:

```bash
npm run preview
```

`vite preview` предназначен для локальной проверки сборки, а не для production-сервера.

## Планируемая предметная функциональность

### Пользовательский сценарий

1. Пользователь открывает каталог и выбирает товар.
2. Frontend запрашивает карточку товара и позволяет начать покупку.
3. Backend создаёт персональную попытку покупки.
4. При доступном товаре пользователь переходит к checkout; иначе попытка получает
   состояние `waiting`.
5. Frontend периодически запрашивает актуальное состояние попытки.
6. После освобождения товара пользователь получает ограниченное по времени
   приглашение и подтверждает переход к checkout.
7. Frontend отображает checkout и итоговое состояние покупки.
8. Если товар закончился, пользователю предлагаются доступные альтернативы.

### Polling и серверное состояние

TanStack Query планируется использовать для каталога, карточки товара, попытки
покупки, позиции в очереди, mutations и альтернативных товаров.

Для активных состояний `waiting`, `invited` и `checkout` предполагается polling с
интервалом 1–2 секунды. После перехода в конечное состояние polling должен
останавливаться. После mutations связанные данные должны обновляться или
инвалидироваться через Query Cache.

Backend остаётся единственным источником истины для состояния очереди, позиции,
резервов и временных ограничений. Frontend не должен самостоятельно продлевать
резерв или переводить попытку в новое состояние без ответа backend.

### Checkout, таймеры и альтернативы

Оставшееся время планируется отображать на основании deadline от backend. Истечение
локального таймера должно инициировать обновление серверного состояния, а не
самостоятельный переход между состояниями.

Checkout и результат оплаты будут отдельными экранами текущего route-каркаса.
Полноценное списание денег остаётся внешней системой. Для `sold_out` планируется
показывать альтернативные доступные товары, полученные от backend.

### Идемпотентность

Для одного намерения пользователя войти в очередь планируется создавать один
`Idempotency-Key`. Повтор запроса после сетевой ошибки должен использовать тот же
ключ, чтобы не создавать дублирующую попытку.
