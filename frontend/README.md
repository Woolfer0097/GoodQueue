# GoodQueue Frontend

Frontend для демонстрации механики очереди на покупку ограниченного товара.

Основная часть проекта — компонент `PurchaseQueueFlow`. Он не зависит от роутинга демонстрационного приложения и может быть встроен в страницу товара существующего React-приложения.

Каталог, выбор демонстрационного пользователя и имитация оплаты нужны только для автономной демонстрации решения.

## Возможности

- просмотр каталога и карточки товара;
- выбор демонстрационного пользователя;
- вход в очередь;
- отображение позиции и количества ожидающих;
- периодическое обновление состояния попытки;
- отмена ожидания;
- временное приглашение к покупке;
- переход в checkout;
- отображение таймера;
- имитация успешной или неуспешной оплаты;
- отображение конечного результата;
- рекомендации альтернативных товаров.

## Пользовательский сценарий

1. Пользователь выбирает товар.
2. Нажимает кнопку покупки.
3. Backend создаёт персональную попытку покупки.
4. При наличии свободного товара попытка сразу переходит в `checkout`.
5. В противном случае пользователь попадает в `waiting`.
6. Frontend периодически запрашивает актуальное состояние попытки.
7. Когда товар освобождается, пользователь получает состояние `invited`.
8. Пользователь подтверждает переход в checkout.
9. После оплаты отображается конечный результат.
10. При недоступности товара пользователю предлагаются альтернативные товары.

## Управление состоянием

TanStack Query используется для серверного состояния:

- списка товаров;
- данных товара;
- текущей попытки покупки;
- позиции пользователя;
- рекомендаций;
- операций входа, отмены и начала checkout;
- периодического обновления состояния.

Локальное состояние React используется для:

- открытых модальных окон;
- состояния кнопок;
- локальных элементов интерфейса;
- выбранного демонстрационного пользователя.

Redux Toolkit и RTK Query не используются.

Backend остаётся единственным источником истины для состояния очереди, позиции пользователя, резервов и временных ограничений.

Приложение использует единый экземпляр `QueryClient` со следующими базовыми настройками:

- данные считаются свежими в течение 30 секунд;
- неуспешный запрос повторяется один раз;
- при возврате фокуса на окно автоматический повторный запрос не выполняется.

React Query Devtools подключаются только в режиме разработки.

## Рендеринг

Frontend работает как CSR-приложение.

SSR для модуля очереди не требуется, поскольку его содержимое персонализировано, зависит от состояния пользователя и постоянно обновляется после загрузки страницы.

Публичное приложение, в которое будет встроен модуль, может использовать SSR независимо от `PurchaseQueueFlow`.

## Интеграция модуля

Пример использования компонента внутри страницы товара:

```tsx
import { PurchaseQueueFlow } from '@/widgets/purchase-queue-flow';

export function ProductPage() {
  return (
    <PurchaseQueueFlow
      apiBaseUrl="http://localhost:8080"
      productId="22222222-2222-2222-2222-222222222222"
      userId="00000000-0000-4000-8000-000000000001"
      onCheckout={(attemptId) => {
        console.log('Checkout attempt:', attemptId);
      }}
    />
  );
}
```

Компонент не должен самостоятельно управлять роутами основного приложения. Переход во внешний checkout выполняется через callback.

### Mock-режим

Для разработки интерфейса backend можно запустить без PostgreSQL:

```bash
GOODQUEUE_MODE=mock go run ./cmd/goodqueue-backend
```

Mock API:

- использует те же публичные маршруты и JSON-контракты;
- хранит изменения в памяти;
- сбрасывает состояние после перезапуска;
- содержит готовые состояния очереди;
- не запускает фоновые workers;
- не поддерживает internal payment и stock endpoints.

Mock-режим предназначен для разработки интерфейса, а не для проверки полной бизнес-логики.

### Полный режим

Для проверки полного пользовательского сценария:

```bash
cp .env.example .env
make compose-up
```

Docker Compose поднимает PostgreSQL, выполняет миграции, запускает backend и включает демонстрационный payment callback.

## API

### Публичные маршруты

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/v1/products` | Получить товары |
| `GET` | `/api/v1/products/:productID` | Получить товар |
| `GET` | `/api/v1/products/:productID/alternatives` | Получить альтернативные товары |
| `GET` | `/api/v1/demo/users` | Получить демонстрационных пользователей |
| `POST` | `/api/v1/products/:productID/queue-entries` | Войти в очередь |
| `GET` | `/api/v1/products/:productID/queue-entry` | Получить текущую или последнюю попытку |
| `DELETE` | `/api/v1/products/:productID/queue-entry` | Отменить активную попытку |
| `POST` | `/api/v1/queue-attempts/:attemptID/checkout` | Начать checkout |

### Внутренний маршрут демонстрационной оплаты

```text
POST /internal/v1/payment-events
```

Маршрут доступен только при явном включении небезопасного демонстрационного callback. Он не должен использоваться в production.

## Заголовки запросов

Для идентификации демонстрационного пользователя:

```http
X-User-ID: <user-id>
```

Для входа в очередь:

```http
Idempotency-Key: <unique-key>
```

Request body для входа в очередь отсутствует.

Ключ идемпотентности создаётся на одно намерение пользователя войти в очередь. Повтор запроса после сетевой ошибки должен использовать тот же ключ.

## Состояния попытки

| Состояние | Описание |
|---|---|
| `waiting` | Пользователь ожидает освобождения товара |
| `invited` | Товар временно зарезервирован, необходимо начать checkout |
| `checkout` | Checkout начат, ожидается результат оплаты |
| `purchased` | Покупка завершена |
| `invite_expired` | Время приглашения истекло |
| `checkout_expired` | Время checkout истекло |
| `payment_failed` | Оплата завершилась ошибкой |
| `cancelled` | Пользователь отменил попытку |
| `sold_out` | Товар закончился |

Экран определяется серверным состоянием попытки. Frontend не хранит отдельный дублирующий статус пользовательского сценария.

## Обновление состояния

Для активных состояний используется polling через TanStack Query:

```text
waiting
invited
checkout
```

Polling прекращается после перехода в конечное состояние.

Рекомендуемый интервал запросов:

```text
1000–2000 мс
```

После успешных mutations соответствующие query инвалидируются или обновляются через Query Cache.

## Таймеры

Frontend отображает оставшееся время на основании deadline, полученного от backend.

Frontend не должен:

- самостоятельно продлевать резерв;
- считать локальный таймер источником истины;
- переводить попытку в новое состояние без ответа backend.

После истечения отображаемого времени выполняется повторный запрос состояния.

## CORS

## Тестирование

В первую очередь покрываются критические пользовательские сценарии:

- успешная загрузка товаров;
- вход в очередь;
- повторный запрос с тем же ключом идемпотентности;
- переход сразу в `checkout`;
- отображение позиции в `waiting`;
- переход `waiting → invited`;
- начало checkout;
- отмена ожидания;
- истечение приглашения;
- истечение checkout;
- успешная оплата;
- неуспешная оплата;
- состояние `sold_out`;
- состояние `queue_disabled`;
- переполнение очереди;
- рекомендации альтернативных товаров;
- ошибки сети и API.

Для модульных frontend-тестов API мокируется. Полная конкурентная бизнес-логика проверяется тестами backend.

## Ограничения MVP

- полноценная регистрация и авторизация отсутствуют;
- `X-User-ID` используется только для демонстрации;
- полноценный checkout является внешней системой;
- реальный платёжный провайдер не подключён;
- demo payment callback небезопасен и используется только локально;
- frontend получает состояние через polling;
- WebSocket, SSE и реальные уведомления не реализованы;
- frontend не управляет остатками и резервами;
- mock-режим не моделирует payment, TTL workers и reconciliation.
