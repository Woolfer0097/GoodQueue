# GoodQueue Frontend

Frontend демонстрационного MVP механики очереди на покупку ограниченного товара.

Проект реализует сквозной пользовательский сценарий: каталог, очередь, временный резерв,
границу checkout и экран результата. Состояние покупки и все переходы подтверждает backend.

## Текущее состояние

Уже реализовано:

- CSR-приложение на React 19, TypeScript и Vite;
- `BrowserRouter` и каркас маршрутов;
- общий layout на Mantine `AppShell`;
- тема Mantine, системные уведомления и индикатор сетевой активности;
- единый `QueryClient` и React Query Devtools в development-режиме;
- общие схемы валидации непустой строки и UUID;
- базовый HTTP-клиент в `src/shared/api`;
- entity товара: валидируемые запросы списка, детали и альтернатив, пользовательская
  доступность и `ProductCard`;
- адаптивный каталог товаров с loading, empty и error states;
- страница товара с loading, not found и error states и вторичным блоком похожих товаров;
- хлебные крошки на странице товара и всех этапах покупки;
- страница 404 для неизвестных frontend-маршрутов;
- entity демонстрационного пользователя: валидируемый запрос списка и сохраняемый выбор;
- feature выбора demo-пользователя в общем layout;
- entity попытки покупки: Zod-модель и запрос текущего attempt для товара и выбранного
  demo-пользователя;
- вход в очередь с CTA на странице товара, scoped `Idempotency-Key` и маршрутизацией по
  возвращённому backend state;
- polling активной попытки покупки с маршрутизацией по фактическому state backend;
- экран ожидания с восстановлением attempt по URL, позицией, общим числом ожидающих,
  отменой через backend и похожими товарами;
- экран персонального временного резерва для `invited` с server-deadline countdown,
  переходом к checkout через backend и отменой;
- экран checkout с товаром, ценой, подтверждением персонального временного права,
  server-deadline countdown, отменой покупки и маршрутизацией строго по ответу backend;
- экран результата для всех terminal states с восстановлением attempt по URL, возвратом
  active states на соответствующий экран и похожими товарами для recoverable негативных
  исходов;
- переключатель светлой и тёмной темы рядом с выбором demo-пользователя;
- конфигурация Jest, React Testing Library, ESLint, Steiger и Prettier;
- route-компоненты полного демонстрационного сценария.

Границы MVP:

- авторизация, создание заказа и списание денег остаются внешними системами;
- frontend не вызывает внутренний payment callback и не создаёт платёжные исходы;
- сценарий пока поставляется как приложение, а не как готовый к встраиванию виджет.

## Архитектура

Исходный код организован по Feature-Sliced Design:

- `src/app` — композиция приложения, провайдеры, маршрутизация, тема и layout;
- `src/entities` — предметные модели, API и переиспользуемый UI сущностей;
- `src/features` — законченные пользовательские действия;
- `src/widgets` — переиспользуемые композиционные блоки страниц;
- `src/pages` — route-компоненты экранов;
- `src/shared` — общая инфраструктура без предметной логики.

Предметные API-функции и DTO располагаются рядом с реализующими их сущностями и
сценариями, а не в `shared/api`.

## Реализованная инфраструктура

### Провайдеры приложения

Приложение обёрнуто в:

- `QueryClientProvider` для серверного состояния;
- `MantineProvider` с общей темой;
- `BrowserRouter` для клиентской маршрутизации.

Системные уведомления отображаются в правом верхнем углу, не более трёх
одновременно. Индикатор навигации реагирует на активные запросы и мутации TanStack
Query. Background-запросы, помеченные через query `meta`, не запускают глобальный
индикатор. React Query Devtools подключаются только в development-режиме.

Для запросов заданы базовые настройки:

- `staleTime` — 30 секунд;
- повтор неуспешного запроса — один раз;
- повторный запрос при возврате фокуса на окно отключён.

### Маршрутизация

Каркас приложения содержит маршруты:

| Маршрут                            | Route-компонент      |
| ---------------------------------- | -------------------- |
| `/`                                | `CatalogPage`        |
| `/products/:productId`             | `ProductDetailsPage` |
| `/products/:productId/queue`       | `QueuePage`          |
| `/products/:productId/reservation` | `ReservationPage`    |
| `/products/:productId/checkout`    | `CheckoutPage`       |
| `/products/:productId/result`      | `ResultPage`         |
| `*`                                | `NotFoundPage`       |

`CatalogPage` отображает каталог товаров, `ProductDetailsPage` — выбранный товар,
`QueuePage` — актуальное ожидание в очереди, `ReservationPage` — персональный временный
резерв, `CheckoutPage` — подтверждённое backend право на покупку,
`ResultPage` — фактический terminal state, а `NotFoundPage` обрабатывает неизвестные
frontend-маршруты.

На всех маршрутах товара отображается единая навигационная цепочка: каталог, товар и,
если применимо, текущий этап покупки. Текущий пункт не является ссылкой и помечен через
`aria-current="page"`; корневой каталог не дублирует сам себя хлебными крошками.

Для `checkout_expired` и `payment_failed` действие «Повторить покупку» сразу создаёт
новую попытку через backend и направляет пользователя на экран фактического состояния
ответа. Для `invite_expired` и `cancelled` результат возвращает пользователя на страницу
товара без автоматического создания попытки.

Маршрут для фактического состояния попытки покупки определяется общей функцией
`getQueueAttemptRoute` из `entities/queue-attempt`. Join, polling и route-страницы используют
одно правило и не хранят бизнес-состояние в React Router state.

### Shared API

`src/shared/api` содержит только общую инфраструктуру взаимодействия с backend:

- `apiClient<ResponseData>(path, init?)` — типизированная обёртка над `fetch`;
- base URL из `VITE_API_URL`;
- разбор JSON, текстовых и пустых ответов;
- `ApiError` для неуспешных HTTP-ответов со свойствами `status`, `statusText` и
  `data`.

Публичные экспорты доступны через `src/shared/api/index.ts`:

```ts
import { apiClient, ApiError } from '@/shared/api';
```

Клиент принимает стандартный `RequestInit`; заголовки и тело конкретного запроса
задаёт вызывающий предметный модуль. Ошибки сети, при которых HTTP-ответ не был
получен, остаются исходными ошибками `fetch`.

### Общая валидация

`src/shared/lib/validation` экспортирует схемы непустой строки и UUID. Предметные
схемы будут размещаться ближе к соответствующим `entities` и `features`, используя
общие схемы как строительные блоки.

### Товары

`src/entities/product` предоставляет валидируемые запросы списка, детали и альтернатив
товара. Alternatives имеют отдельный query key и загружаются только при вызове
`useProductAlternativesQuery(productId)`; каталог их заранее не запрашивает.

Swagger-ответ alternatives содержит все обязательные поля товара и дополнительно может
содержать `reason_code`, `recommendation_mode` и `recommendation_score`. Схема
alternatives расширяет существующую `productSchema`, валидирует эти метаданные и
сохраняет совместимость результата с `Product` и `ProductCard`.

`src/widgets/relevant-products` собирает вторичный блок «Похожие товары» из существующих
query и `ProductCard`. Блок отображает весь ответ backend в адаптивной `SimpleGrid` без
дополнительного клиентского лимита; актуальный backend-контракт ограничивает результат
четырьмя товарами. Виджет использует общий с каталогом `ProductCardSkeleton`, обрабатывает
empty/error/retry states и защитно исключает исходный товар. Alternatives помечены как
background query: их загрузка или обновление не блокируют основной экран и не запускают
глобальный navigation progress.

На `ProductDetailsPage` похожие товары загружаются только после успешной загрузки основного
товара и располагаются ниже информации и CTA покупки. На `QueuePage` блок показывается
только для подтверждённого состояния `waiting`, ниже статуса очереди и действия отмены.

### Демонстрационный пользователь

`src/entities/demo-user` описывает контракт `GET /api/v1/demo/users` через Zod,
загружает и валидирует список через общий HTTP-клиент и предоставляет стабильный
query key и TanStack Query hook.

`CurrentDemoUserProvider` подключён на уровне провайдеров приложения. Публичный hook
`useCurrentDemoUser()` возвращает выбранного пользователя и его `userId`, который
queue-сценарии используют для заголовка `X-User-ID`, не связывая
само состояние выбора с queue API. В `localStorage` хранится только UUID. После
загрузки списка отсутствующий или некорректный UUID заменяется первым доступным
пользователем; при пустом списке сохранённое значение удаляется.

Feature `src/features/select-demo-user` отображается как плавающий demo-инструмент:
кнопка с аватаром и именем текущего пользователя открывает popover с Mantine `Select`.
Feature обрабатывает загрузку, ошибку и пустой список и не выполняет queue-запросы.
Публичный API feature также экспортирует `useCurrentDemoUser()`, чтобы сценарии очереди
получали выбранный `userId` без доступа к внутренним модулям feature.

Слева от выбора demo-пользователя находится переключатель светлой и тёмной темы.
Выбранная цветовая схема сохраняется встроенным менеджером Mantine.

### Попытка покупки

`src/entities/queue-attempt` описывает фактический Swagger-контракт попытки покупки
через Zod и выводит TypeScript-типы из схем. Entity предоставляет запрос
`GET /api/v1/products/:productID/queue-entry`, передаёт выбранный `userId` в
`X-User-ID` и валидирует успешный ответ backend.

Ответ `404` этого endpoint означает отсутствие attempt и преобразуется в `null` как
нормальное серверное состояние. Остальные ошибки не скрываются. Query key включает
`productId` и `userId`, поэтому переключение demo-пользователя не переиспользует
чужой cache.

Feature `src/features/join-queue` выполняет
`POST /api/v1/products/:productID/queue-entries` для выбранного demo-пользователя.
Действие на странице товара сначала учитывает текущую попытку выбранного пользователя.
Без попытки показывается `Купить` при свободном остатке или `Встать в очередь`, если
товар доступен только через ожидание. Для `waiting`, `invited` и `checkout` новый join
заменяется ссылкой на текущий этап. После recoverable terminal state доступно
актуальное действие по доступности товара: `Купить`, `Встать в очередь` или недоступное
состояние покупки/очереди. После `purchased` и `sold_out` доступен только переход к результату.
Пока attempt загружается или завершился ошибкой, новая покупка не предлагается.
Кнопка join показывает loading и блокируется на время mutation.
Успешный ответ сохраняется в queue-attempt cache, после чего существующий
`getQueueAttemptRoute` выбирает queue, reservation, checkout или result непосредственно
по состоянию backend. `queue_disabled` и технические ошибки остаются на странице товара
и показываются пользовательским уведомлением без raw `ApiError`.

Для нового намерения входа создаётся отдельный `Idempotency-Key`. После сетевой или
server-ошибки повтор использует тот же ключ; успешный join или бизнес-ошибка завершает
это намерение.

Feature `src/features/queue-polling` опрашивает attempt каждые 1,5 секунды только в
состояниях `waiting`, `invited` и `checkout`. После terminal state polling
останавливается. Query помечен как background, поэтому уже загруженные данные остаются
на экране при refetch, а глобальный navigation progress не запускается. Маршрутизация
централизована в `getQueueAttemptRoute`: `waiting` ведёт в очередь, `invited` — в резерв,
`checkout` — в оформление, terminal state — в результат. При смене demo-пользователя
используется отдельный cache key; без `productId` или `userId` запрос не выполняется.
Страница самого товара остаётся доступной при любом состоянии attempt: текущее состояние
не выталкивает пользователя обратно в queue flow, но персонализирует статус и CTA.
Автоматический переход выполняется, когда background polling получает новое состояние backend.

`QueuePage` получает `productId` из маршрута и отображает только подтверждённый backend
state `waiting`. Первая загрузка использует Skeleton, а background polling сохраняет
контент на экране. Позиция и общее число ожидающих показываются только при наличии этих
полей в queue-entry. Счётчик времени в очереди увеличивается от серверного `created_at`;
ETA и искусственный progress не рассчитываются.

Похожие товары в состоянии `waiting` запрашиваются по `productId` исходного route и
располагаются после основного действия очереди. При переходе в `cancelled` ResultPage
использует тот же исходный `productId` и query key, поэтому уже загруженный список
переиспользуется из кэша и не пересчитывается относительно выбранной рекомендации.

При отсутствии attempt прямой URL очереди возвращает пользователя на страницу товара с
понятным уведомлением. Другой backend state направляет на reservation, checkout или
result. Feature `src/features/cancel-queue` выполняет `DELETE queue-entry`, после чего
сохраняет возвращённый backend attempt, если он присутствует. Для текущего ответа
`204 No Content` feature повторно запрашивает `GET queue-entry`, инвалидирует queue
queries и заменяет активный cache подтверждённым backend state. Поэтому stale
`waiting`/`invited` не остаётся источником маршрутизации, а `cancelled` направляет на
result только после ответа backend.

`ReservationPage` отображает только подтверждённый backend state `invited`. Для срока
используется `deadline_at`, а при его отсутствии — совместимое поле `expires_at` из
`GET queue-entry`. Countdown каждый раз вычисляется относительно server deadline и
текущего времени; он не хранит локальный state attempt и при `00:00` только запрашивает
attempt повторно. Background refetch может заменить deadline без сброса страницы.

Внутреннее действие `ReservationPage` вызывает фактическую Swagger-операцию
`POST /api/v1/queue-attempts/:attemptID/checkout` и сохраняет возвращённый backend
attempt в Query Cache. Оно расположено в page-slice, потому что не переиспользуется за
пределами сценария резерва. Переход на checkout выполняется общей маршрутизацией лишь
после получения состояния `checkout`; локальный countdown не создаёт `invite_expired`
и не отправляет отдельный expire request.

`CheckoutPage` является границей MVP: он подтверждает, что backend допустил выбранного
пользователя к покупке, но не имитирует отсутствующие оформление заказа и оплату.
Пользователь может отказаться от покупки через существующий
`src/features/cancel-queue`; backend освобождает резерв и возвращает подтверждённое
terminal-состояние. `purchased` и `payment_failed` могут появиться только из последующего
опроса backend после результата внешнего checkout или демонстрационного payment callback.
Frontend не вызывает внутренний `/internal/v1/payment-events` и не создаёт платёжные
исходы самостоятельно.

## Локальная конфигурация

Frontend использует `VITE_API_URL` как base URL backend. Шаблон настройки находится
в `.env.example`:

```env
VITE_API_URL=http://localhost:8080
```

Перед локальным запуском создайте `frontend/.env` из шаблона.

PowerShell:

```powershell
Copy-Item .env.example .env
```

Bash:

```bash
cp .env.example .env
```

Локальные адреса по умолчанию:

- frontend — <http://localhost:5173>;
- backend — <http://localhost:8080>;
- Swagger UI backend — <http://localhost:8080/docs>.

Backend должен разрешать CORS для origin frontend. Настройка и запуск backend
описаны в корневом README проекта.

## Локальный запуск

Требования:

- Node.js `>=24.19.0 <25` (`24.19.0` зафиксирована в `.nvmrc` для разработки);
- npm;
- доступный backend на адресе из `VITE_API_URL` для предметных запросов.

Из директории `frontend`:

```bash
npm ci
npm run dev
```

Vite запустит development-сервер на <http://localhost:5173>.

## Production-сборка

Проверка типов и production-сборка выполняются одной командой:

```bash
npm run build
```

Результат создаётся в `frontend/dist`.

Для локального просмотра уже собранного приложения:

```bash
npm run preview
```

`vite preview` предназначен для локальной проверки сборки, а не для production-сервера.

Production-образ собирается из директории `frontend` с обязательным build argument:

```bash
docker build --build-arg VITE_API_URL=http://localhost:8080 -t goodqueue-frontend .
```

`VITE_API_URL` встраивается Vite в статические файлы во время `npm run build`.
Изменение переменной окружения при запуске готового контейнера не меняет адрес
backend: для другого адреса необходимо пересобрать образ с новым build argument.

Multi-stage Dockerfile использует Node.js только для сборки. Production-образ на
Nginx содержит собранный `dist` и конфигурацию раздачи статики с fallback на
`index.html` для маршрутов React Router.

## Реализованный пользовательский сценарий

### Пользовательский сценарий

1. Пользователь открывает каталог и выбирает товар.
2. Frontend запрашивает карточку товара и позволяет начать покупку.
3. Backend создаёт персональную попытку покупки.
4. При доступном товаре пользователь переходит к checkout; иначе попытка получает
   состояние `waiting`.
5. Frontend периодически запрашивает актуальное состояние попытки.
6. После освобождения товара пользователь получает ограниченное по времени
   приглашение и подтверждает переход к checkout.
7. Frontend отображает персональное право на checkout. Итоговое состояние появляется
   только после ответа backend, получившего результат от внешнего checkout.
8. Если товар закончился, пользователю предлагаются доступные альтернативы.

### Polling и серверное состояние

TanStack Query используется для каталога, карточки товара, попытки покупки, входа в
очередь, позиции, отмены ожидания, старта и повторного подтверждения checkout и
альтернативных товаров.

Для активных состояний `waiting`, `invited` и `checkout` выполняется polling с интервалом
1,5 секунды. После перехода в конечное состояние polling останавливается. После
mutations связанные данные обновляются или инвалидируются через Query Cache.

Backend остаётся единственным источником истины для состояния очереди, позиции,
резервов и временных ограничений. Frontend не должен самостоятельно продлевать
резерв или переводить попытку в новое состояние без ответа backend.

### Checkout, таймеры и альтернативы

На экране резерва оставшееся время отображается на основании deadline от backend.
Истечение визуального countdown инициирует обновление серверного состояния, а не
самостоятельный переход между состояниями. Checkout также показывает server-deadline
countdown и не изменяет state самостоятельно.

Checkout и результат оплаты используют отдельные экраны текущего route-каркаса.
Полноценное списание денег остаётся внешней системой. ResultPage восстанавливает
terminal state из backend и показывает похожие товары после `sold_out`, `payment_failed`,
`checkout_expired` и `cancelled`. После `purchased` и `invite_expired` блок не показывается:
для них основным следующим шагом остаётся завершение сценария или повтор исходной попытки.

### Идемпотентность

Для одного намерения пользователя войти в очередь создаётся один
`Idempotency-Key`. Повтор запроса после сетевой ошибки должен использовать тот же
ключ, чтобы не создавать дублирующую попытку. После завершения намерения следующая
попытка получает новый ключ.
