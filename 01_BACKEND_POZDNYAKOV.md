# Backend A — Поздняков: Инфраструктура и данные

## Твоя зона ответственности

Ты отвечаешь за фундамент: как поднимается проект, как устроена база данных, как данные читаются/пишутся, и как гарантируется, что при параллельных запросах не возникнет гонки за товар. Твой код — самый нижний слой (`repository`), от которого зависят Кочегаров (service) и опосредованно Любченко (handler). Работай в первую очередь и быстро — ты разблокируешь остальных.

Работаешь против интерфейсов, которые описаны в `domain` (модели `Product`, `QueueEntry`, интерфейсы `ProductRepository`, `QueueRepository`) — их фиксируете все вместе в первый час.

## Задача: Docker-compose: Postgres + backend-заглушка

**Зачем:** нужно, чтобы весь проект поднимался одной командой (`docker-compose up`) с первого дня — это критерий оценки «доступность/воспроизводимость» и просто экономит время под конец, когда обычно вылезают проблемы с деплоем.

**Как:**
- Сервис `postgres` (образ `postgres:16-alpine`), с переменными окружения для базы/юзера/пароля, volume для персистентности данных.
- Сервис `backend` — собирается из `/backend/Dockerfile`, зависит от `postgres` (`depends_on`), пробрасывает порт (например 8080).
- Сразу добавь `.env`/переменные окружения с `DATABASE_URL`, чтобы конфиг не хардкодился.
- Backend на этом этапе может быть просто «Hello World» HTTP-сервером — важно, чтобы контейнер собирался и стартовал.

**Результат:** `docker-compose up` поднимает Postgres и заглушку бэкенда без ошибок.

## Задача: Миграции: таблицы products, queue_entries, users

**Зачем:** это структура данных, на которой строится вся бизнес-логика. Продумать её сразу правильно — значит не переделывать потом на середине хакатона.

**Как:**
- Используй любой инструмент миграций (goose, golang-migrate, или просто SQL-файлы с `up`/`down`).
- `products`: id, title, description, price, image_url, category, stock, reserved, created_at. Обрати внимание: `reserved` — это количество единиц, сейчас занятых активными правами (`granted`). Доступное количество = `stock - reserved`, не храни его отдельным полем, чтобы не было рассинхрона.
- `queue_entries`: id, product_id (FK), user_id, status (enum: waiting/granted/purchased/expired/rejected/cancelled), created_at, granted_at, expires_at, finished_at.
- `users`: id, name — упрощённая заглушка вместо полноценной авторизации (её реализовывать не нужно по условиям кейса).
- Добавь индексы: `(product_id, status)` — воркер Кочегарова будет искать `waiting`-заявки по товару; `(status, expires_at)` — воркер будет искать протухшие `granted`-заявки по всем товарам; `(user_id)` — для истории пользователя.
- Добавь CHECK-constraint `reserved <= stock` на уровне БД — дополнительная страховка от логической ошибки в коде.

**Результат:** миграции применяются командой (`up`), схема соответствует модели из `domain`.

## Задача: Seed-скрипт с тестовыми товарами и пользователями

**Зачем:** без тестовых данных ни фронт, ни остальные бэкендеры не смогут проверять сценарии. Особенно важен товар с `stock=1` — это единственный способ наглядно продемонстрировать защиту от гонки.

**Как:**
- Минимум 3 товара:
  - Товар А: `stock=1` — для теста гонки (несколько пользователей одновременно).
  - Товар Б: `stock=3-5` — чтобы показать, как очередь двигается по нескольким пользователям подряд.
  - Товар В: `stock=0` изначально или сразу «раскупленный» — для демонстрации сценария `rejected`/«похожие товары».
- Минимум 3-5 тестовых пользователей в `users` (например, «Пользователь 1», «Пользователь 2»...).
- Реализуй как отдельный SQL-файл миграции (`0002_seed.up.sql`) или Go-скрипт, который можно перезапускать для сброса демо-данных.

**Результат:** после `docker-compose up` в базе уже есть данные, готовые для демонстрации всех сценариев.

## Задача: Реализовать repository с базовыми CRUD-методами

**Зачем:** это слой, через который Кочегаров и Любченко будут читать/писать данные, не заботясь о деталях SQL. Чем раньше он готов (пусть даже без сложной транзакционной логики) — тем раньше остальные могут подключиться к реальной БД вместо моков.

**Как:**
- Реализуй интерфейсы `ProductRepository` и `QueueRepository` из `domain` над реальным подключением к Postgres (используй `pgx` или `database/sql` — на твой выбор).
- Базовые методы: `GetProduct(id)`, `CreateQueueEntry(...)`, `GetQueueEntry(id)`, `UpdateQueueEntryStatus(id, status)`, `ListWaitingEntries(productID)` и т.п. — конкретный список смотри в файле `domain`, который вы зафиксируете вместе.
- На этом этапе НЕ обязательно делать транзакционную защиту от гонки — это следующая задача. Сначала — просто рабочий CRUD.

**Результат:** Кочегаров может подключить свой `service` к реальной БД вместо in-memory заглушки.

## Задача: Транзакции + SELECT ... FOR UPDATE для атомарной резервации

**Зачем:** это ядро защиты от главного риска всего кейса — что два пользователя одновременно получат право на последнюю единицу товара. Без этого механизма продукт не выполняет ключевое требование задачи («система не должна допускать ситуации, когда несколько пользователей одновременно получают возможность купить один и тот же товар»).

**Как:**
- Метод выдачи права должен быть обёрнут в одну транзакцию:
  1. `SELECT stock, reserved FROM products WHERE id = $1 FOR UPDATE` — блокирует строку товара до конца транзакции, не давая другому параллельному запросу прочитать те же значения.
  2. Проверка: `stock - reserved > 0`.
  3. Если есть свободный слот: `UPDATE products SET reserved = reserved + 1 WHERE id = $1` и `UPDATE queue_entries SET status='granted', granted_at=now(), expires_at=now()+interval '2 minutes' WHERE id = $2`.
  4. `COMMIT`.
- Если слота нет — транзакция откатывается, заявка остаётся в `waiting`.
- Аналогичная атомарность нужна при освобождении слота (когда `granted` переходит в `expired` или `purchased` — нужно уменьшить `reserved`).

**Как проверить, что работает:** напиши небольшой тест или скрипт, который параллельно (например, 10 горутин) пытается получить право на товар с `stock=1` — в результате должно быть выдано ровно одно право, остальные должны остаться в очереди или получить его позже по одному.

**Результат:** атомарность гарантирована на уровне БД, race condition невозможен даже при параллельных запросах.

## Задача: Индексы под частые запросы: status, product_id, expires_at

**Зачем:** без индексов при увеличении числа записей в очереди (даже в рамках демо со множеством тестовых прогонов) запросы воркера («найти всех protuhших `granted`», «найти всех `waiting` по товару») станут делать полный скан таблицы — для хакатона это не критично по производительности, но правильные индексы — это признак качественной архитектуры, что тоже оценивается.

**Как:**
- Если не сделал в миграции (задача выше), добавь сейчас: `CREATE INDEX ON queue_entries(product_id, status);` и `CREATE INDEX ON queue_entries(status, expires_at);`.
- Проверь через `EXPLAIN ANALYZE` на тестовых данных, что индексы реально используются в запросах воркера.

**Результат:** ключевые запросы воркера используют индексы, а не последовательное сканирование.

## Задача: Нагрузочный скрипт с параллельными запросами

**Зачем:** нужно доказать (себе, команде и жюри), что атомарность реально работает — не просто «по коду вроде должно», а проверено эмпирически.

**Как:**
- Напиши простой Go-скрипт (или используй `hey`/`ab`/`k6`), который отправляет N параллельных POST-запросов на `/api/products/{id}/queue` для товара с `stock=1`.
- После выполнения проверь в БД: сколько записей получили статус `granted` — должно быть ровно `stock`.
- Задокументируй результат — это отличный аргумент в раздел README «как мы защитились от гонки».

**Результат:** воспроизводимый тест, показывающий корректность атомарной резервации.
