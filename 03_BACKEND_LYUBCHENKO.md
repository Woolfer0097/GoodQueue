# Backend C — Любченко: API и интеграция с фронтом

## Твоя зона ответственности

Ты — точка контакта между бэкендом и фронтендом. Твой слой (`handler`) превращает бизнес-логику Кочегарова в реальный HTTP API, который использует фронт. Ты отвечаешь за то, чтобы контракт API был стабильным, понятным и защищённым — в частности, именно в твоём слое проверяется, что систему нельзя обойти прямым запросом.

Работаешь против интерфейса `QueueService` из `domain` — сначала на заглушке от Кочегарова, потом на реальной реализации.

---

## Задача: Зафиксировать API-контракт с фронтом

**Зачем:** это первая задача всего проекта, от которой зависит независимая параллельная работа фронта и бэка. Пока контракт не зафиксирован, фронт не может начать верстать даже на моках, а ты не можешь спроектировать хендлеры.

**Как:**
- Проведи короткую встречу с фронтендером (30-40 минут) в первый час проекта.
- Зафиксируйте на бумаге/в общем документе точные эндпоинты, форматы запросов и ответов:

```
GET  /api/products/{id}
→ { "id", "title", "description", "price", "image_url", "category", "available" }

POST /api/products/{id}/queue
Body: { "user_id": "uuid" }
→ { "entry_id": "uuid", "status": "waiting", "position": 3 }

GET  /api/queue/{entry_id}
→ { "entry_id", "status", "position"?, "expires_at"? }

POST /api/queue/{entry_id}/purchase
→ 200 { "status": "purchased" }
→ 409 { "error": "grant expired or invalid" }

DELETE /api/queue/{entry_id}
→ 200 (вышел из очереди)
```
- Проговорите отдельно формат ошибок (единая структура `{ "error": "..." }` для всех эндпоинтов) — это упростит обработку на фронте.
- Зафиксируйте статусы (enum), которые может отдавать API — сверьте со state machine, которую проектирует Кочегаров.

**Результат:** документ с контрактом, на который фронт может ориентироваться при верстке моков, не дожидаясь тебя.

## Задача: Роутинг + скелет хендлеров под контракт API

**Зачем:** нужен работающий (пусть пока пустой внутри) HTTP-сервер с правильными путями, методами и форматом ответов — чтобы фронт мог подключиться к реальным URL уже на раннем этапе, даже если внутри пока заглушки.

**Как:**
- Выбери роутер (стандартный `net/http` + `http.ServeMux`, либо `chi`/`gorilla/mux` — что удобнее команде).
- Зарегистрируй все эндпоинты из контракта, каждый пока возвращает статичный/фейковый JSON-ответ, соответствующий согласованному формату.
- Добавь middleware для CORS (фронт скорее всего будет на другом порту/домене при локальной разработке) и для логирования запросов.
- Структурируй код: `router.go` для регистрации маршрутов, отдельные файлы `product_handler.go`, `queue_handler.go`.

**Результат:** сервер отвечает на все нужные пути с правильными форматами (пока фейковыми данными).

## Задача: Хендлеры на заглушке service, отдают моки фронту

**Зачем:** пока Кочегаров дорабатывает реальную логику state machine, ты можешь уже подключить свои хендлеры к его in-memory заглушке `service` (реализующей тот же интерфейс) — это позволяет фронту переключиться с чисто статичных моков на что-то более похожее на реальное поведение (хотя бы смена статусов вручную/по таймеру в памяти).

**Как:**
- Подключи `QueueService` (интерфейс из `domain`) в конструктор своих хендлеров — на этом этапе это будет реализация-заглушка от Кочегарова.
- Хендлеры должны просто вызывать методы интерфейса и превращать результат в JSON — никакой бизнес-логики в хендлере быть не должно, это чисто «переводчик» между HTTP и `service`.

**Результат:** фронт может делать реальные HTTP-запросы и получать осмысленные (пусть пока не персистентные) ответы.

## Задача: Подключить хендлеры к реальному service от Кочегарова

**Зачем:** финальный шаг интеграции бэкенда — переключение с заглушки на настоящую бизнес-логику, работающую поверх реальной БД.

**Как:**
- В `main.go` при инициализации подставь реальную реализацию `QueueService` (ту, что Кочегаров подключил к repository от Позднякова) вместо заглушки.
- Прогони весь сценарий вручную через Postman/curl: встать в очередь → дождаться `granted` → купить.
- Убедись, что при перезапуске сервера данные не теряются (хранятся в Postgres, а не в памяти).

**Результат:** полностью рабочий бэкенд поверх реальной БД, готовый к финальной интеграции с фронтом.

## Задача: Обработка ошибок и статус-кодов (409 при невалидном праве)

**Зачем:** фронту нужны понятные HTTP-статусы, чтобы корректно обрабатывать разные ситуации (не просто «что-то пошло не так», а конкретно — истекло право, товара нет, неверный запрос).

**Как:**
- Определи маппинг: бизнес-ошибки из `service` (например, `ErrGrantExpired`, `ErrOutOfStock`, `ErrNotFound`) → HTTP-статусы:
  - `404` — товар/заявка не найдены
  - `409` — конфликт состояния (право истекло, статус не тот, для которого разрешено действие)
  - `400` — невалидный запрос (например, отсутствует обязательное поле)
  - `500` — непредвиденная ошибка сервера
- Единый формат тела ошибки: `{ "error": "human readable message", "code": "GRANT_EXPIRED" }` — `code` даёт фронту возможность обрабатывать конкретные случаи программно, а не парсить текст.
- Не забудь логировать реальные ошибки на сервере (для отладки), но не показывать пользователю технические детали (например, текст SQL-ошибки).

**Результат:** фронт может отличать разные типы ошибок и показывать соответствующие сообщения пользователю.

## Задача: Отдать фронту реальный API вместо моков

**Зачем:** формальная точка синхронизации — сообщить фронту, что можно переключаться с локальных моков на реальные запросы к твоему серверу.

**Как:**
- Убедись, что сервер стабильно поднимается локально и/или в docker-compose, дай фронту точный адрес (`http://localhost:8080` или что там у вас).
- Пройдите вместе (созвон/рядом) хотя бы один полный сценарий, чтобы поймать явные нестыковки в формате данных на раннем этапе, а не в последний день.

**Результат:** фронт работает с реальным бэком, а не с заглушками.

## Задача: Защита purchase: проверка status=granted AND expires_at>now() на сервере

**Зачем:** это ключевое требование кейса — «система должна проверять, есть ли у пользователя активное право на покупку именно этого товара» перед переходом к покупке. Это твоя ответственность на уровне HTTP-слоя (хотя основная проверка уже должна быть в `service` у Кочегарова — здесь дублируем как последний рубеж защиты и для правильной обработки HTTP-ответа).

**Как:**
- В хендлере `POST /api/queue/{entry_id}/purchase` перед вызовом `service.Purchase(...)` НЕ делай собственных проверок статуса напрямую в базе — источник истины должен быть один, в `service`. Твоя задача — правильно интерпретировать ошибку, которую вернёт `service`, если условие не выполнено, и превратить её в `409 Conflict` с понятным сообщением.
- Обязательно протестируй руками: попробуй вызвать `purchase` для заявки в статусе `waiting` (без права) — должен быть отказ. Попробуй вызвать после истечения `expires_at` — тоже отказ.
- Это прямая проверка требования «пользователь не может миновать очередь» — задокументируй, как именно это работает, в README.

**Результат:** прямой вызов покупки без действующего права технически невозможен, что бы ни делал пользователь на фронте.

## Задача: Позиция в очереди в ответе API

**Зачем:** улучшает UX — пользователь на экране ожидания видит не абстрактное «ждите», а конкретное «вы 3-й из 7», что снижает тревожность ожидания и попадает в критерий «понятные состояния для пользователя».

**Как:**
- В методе `GetQueueEntry` (или отдельном методе в `service`) добавь подсчёт: сколько записей в статусе `waiting` для этого товара имеют `created_at` раньше, чем у текущей заявки, плюс 1 — это и есть позиция.
- Добавь это поле в ответ `GET /api/queue/{entry_id}` как `position` (может быть `null`/отсутствовать, если статус уже не `waiting`).
- Обсуди с фронтом, нужно ли им ещё и общее количество людей в очереди — если да, добавь и это поле.

**Результат:** фронт может показать пользователю его место в очереди без дополнительных костылей.

## Задача: Похожие товары у других продавцов при expired/rejected

**Зачем:** это прямое попадание в один из вопросов кейса — «почему пользователь останется на платформе, даже если товар закончился». Дешёвая по реализации, но продуктово значимая фича.

**Как:**
- Простой SQL-запрос: найти другие товары той же `category`, у которых `available > 0` (то есть `stock - reserved > 0`), исключая текущий товар, лимит 3-5 штук.
- Добавь эндпоинт (например, `GET /api/products/{id}/similar`) или включи это поле прямо в ответ `GET /api/queue/{entry_id}`, когда статус `expired`/`rejected` — обсуди с фронтом, что удобнее.
- Никакого сложного рекомендательного алгоритма не нужно — простое совпадение по категории полностью закрывает требование для MVP.

**Результат:** пользователь, не успевший купить или опоздавший, видит альтернативные предложения вместо тупика.
