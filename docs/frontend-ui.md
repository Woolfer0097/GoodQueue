# Frontend UI/UX

GoodQueue демонстрирует механику покупки дефицитного товара через пользовательскую очередь.

Интерфейс должен органично восприниматься как часть marketplace: пользователь выбирает товар привычным способом, а механика очереди появляется только тогда, когда она действительно необходима.

Avito используется как референс визуальной иерархии и пользовательского сценария, но GoodQueue не копирует интерфейс Avito целиком.

Основная UI-библиотека проекта — Mantine.

## UX-цель

Пользователь в любой момент должен понимать:

- что происходит с его попыткой покупки;
- доступен ли товар;
- находится ли он в очереди;
- получил ли он право на покупку;
- сколько времени это право действует;
- какое действие доступно дальше.

Интерфейс не должен содержать промежуточных состояний, в которых пользователь не понимает, нужно ли ему ждать, обновлять страницу или совершать какое-либо действие.

Backend является источником истины для состояния товара, очереди, резерва и покупки. Frontend только отображает это состояние.

## Визуальное направление

GoodQueue использует чистый marketplace-интерфейс с высокой информационной плотностью.

Основной фон светлый. Главный акцентный цвет берётся из `avitoBlue` существующей Mantine theme. Цена и название товара имеют более высокий визуальный приоритет, чем технические показатели очереди.

Интерфейс не должен выглядеть как набор dashboard-карточек. Не нужно помещать каждый показатель в отдельный `Paper`, добавлять большое количество рамок, теней и цветных badge.

Mantine theme используется как основной источник spacing, radius, typography и цветов.

## Каталог

Главная страница должна напоминать привычный каталог marketplace: компактная сетка товаров, позволяющая быстро сравнить несколько предложений.

Для layout использовать `Container` и `SimpleGrid`.

Карточка товара строится вокруг изображения. Изображение располагается сверху как на marketplace-карточках Avito. Ниже последовательно отображаются название, цена и краткая информация о доступности.

На desktop карточки остаются вертикальными. Не нужно превращать их в горизонтальные карточки с изображением слева.

В карточке достаточно показывать:

| Данные | Назначение |
| --- | --- |
| Изображение | визуальная идентификация товара |
| Название | понимание выбранного товара |
| Цена | основная коммерческая информация |
| Наличие | возможность купить сейчас |
| Свободно | сколько товаров доступно |
| В очереди | текущий спрос |

`reserved` и другие внутренние показатели механики пользователю в каталоге не показываются.

Если изображения отсутствуют в API, используется единый нейтральный placeholder. Случайные изображения и внешние URL во frontend не добавляются.

Карточка открывает страницу товара. Покупка непосредственно из каталога не начинается.

## Доступность товара

Технические данные backend должны преобразовываться в понятные пользовательские формулировки.

| Состояние | Отображение |
| --- | --- |
| есть `free_stock` | В наличии |
| свободного товара нет, но очередь работает | Доступно по очереди |
| товар закончился | Нет в наличии |
| очередь отключена | Покупка временно недоступна |

Цвет может усиливать состояние, но не заменяет текст.

## Страница товара

Страница товара должна сохранять привычную структуру marketplace.

На desktop изображение остаётся крупным верхним визуальным блоком страницы, а не помещается в искусственную схему «изображение слева — данные справа» только ради использования двух колонок.

В верхней части пользователь видит название, цену и изображение товара. Рядом или непосредственно после основной информации размещаются доступность товара и действие покупки.

Ниже могут отображаться дополнительные данные, которые действительно предоставляет backend.

На mobile сохраняется тот же порядок восприятия: изображение, цена, название, доступность и основное действие.

Не нужно воспроизводить страницу Avito полностью. В GoodQueue отсутствуют продавец, отзывы, доставка, рассрочка, чат, избранное и другие функции, не относящиеся к кейсу.

Главный CTA страницы — `Купить`.

Кнопка покупки появляется только вместе с рабочей логикой queue flow. Не должно быть кнопки, ведущей на фиктивный экран.

## Переход в очередь

После нажатия `Купить` пользователь не должен разбираться в технической механике системы.

На время запроса кнопка показывает loading state и блокирует повторное нажатие.

Дальнейший экран определяется ответом backend.

Если товар нельзя выделить сразу, пользователь переходит в `waiting`.

Если товар может быть сразу закреплён за пользователем, промежуточный экран ожидания может быть пропущен.

Таким образом frontend не имитирует очередь там, где ожидание фактически не требуется.

## Экран ожидания

Главная UX-задача экрана — снизить неопределённость.

Пользователь должен увидеть понятное сообщение о том, что он находится в очереди, а система продолжает проверять возможность покупки автоматически.

Если backend предоставляет данные позиции, показываются позиция и число ожидающих.

Не нужно показывать искусственный progress bar или расчётное время ожидания, если backend не способен достоверно их вычислить.

Polling выполняется в фоне. Он не должен мигать интерфейсом, повторно показывать Skeleton или постоянно запускать глобальный progress indicator.

Основное доступное действие — `Выйти из очереди`.

## Право на покупку

Получение `invited` должно восприниматься как главное позитивное событие сценария.

Пользователь получает явное сообщение:

**Товар зарезервирован для вас**

Рядом отображается оставшееся время действия резерва и основное действие `Перейти к оформлению`.

Временное ограничение должно быть хорошо заметно, потому что оно является частью бизнес-механики, но интерфейс не должен искусственно создавать тревожность.

Frontend считает countdown по серверному deadline только для отображения. При достижении нуля выполняется запрос актуального состояния. Frontend не переводит резерв в expired самостоятельно.

## Checkout

Полноценное оформление заказа и реальная оплата не входят в рамки кейса.

Экран checkout должен демонстрировать главное продуктовое свойство системы: пользователь был допущен к покупке только после получения персонального временного права.

Если право также ограничено временем, оставшийся срок отображается пользователю.

Интерфейс не должен создавать видимость полноценного checkout Avito, которого фактически нет в MVP. Действие оплаты явно маркируется как демонстрационное и не обещает реального списания денег.

## Финальные состояния

Финальный экран не должен быть одинаковым сообщением для всех исходов.

| Состояние | Сообщение | Следующий шаг |
| --- | --- | --- |
| `purchased` | Покупка подтверждена | завершить сценарий или начать новую покупку того же товара |
| `cancelled` | Вы вышли из очереди | вернуться к товару |
| `invite_expired` | Время резерва истекло | попробовать снова |
| `checkout_expired` | Время оформления истекло | повторить покупку |
| `payment_failed` | Не удалось завершить покупку | повторить или выбрать другой товар |
| `sold_out` | Товар закончился | посмотреть альтернативы |

Негативный исход не должен становиться тупиком.

Особенно для `sold_out` пользователь должен получить доступ к похожим доступным товарам. Это помогает сохранить пользователя внутри marketplace после того, как первоначальный товар стал недоступен.

Для альтернатив используется та же `ProductCard`, что и в основном каталоге.

## Demo user

Выбор demo-пользователя является инструментом демонстрации хакатонного решения, а не частью реального marketplace UX.

Он должен быть заметен проверяющему, но визуально отделён от основного пользовательского сценария.

Для выбора использовать Mantine `Select`.

Переключение пользователя позволяет на защите быстро показать разные подготовленные состояния mock API без ручного изменения запросов или данных.

## Loading и фоновые обновления

Первая загрузка каталога или товара отображается через `Skeleton`.

При background refetch уже загруженный контент остаётся на экране.

Polling очереди не должен визуально восприниматься как повторная загрузка страницы.

`NavigationProgress` следует использовать для пользовательски значимых переходов и запросов, но не запускать на каждый polling request.

## Ошибки

Технические ошибки преобразуются в пользовательские сообщения.

Вместо:

`HTTP request failed: 409 Conflict`

показывается, например:

**Не удалось войти в очередь. Попробуйте ещё раз.**

Для ошибок загрузки страницы использовать Mantine `Alert`. Для результата отдельного действия допустимы `notifications`.

Если запрос можно безопасно повторить, пользователю предоставляется действие `Повторить`.

## Empty и 404

Для пустого каталога использовать Mantine `EmptyState` с коротким сообщением о том, что товары пока недоступны.

404 должна содержать только необходимую информацию: страница не найдена и действие возврата к каталогу.

## Mantine

При реализации сначала проверяется наличие подходящего решения в Mantine.

Основные компоненты проекта:

| Задача | Mantine |
| --- | --- |
| оболочка приложения | `AppShell` |
| ограничение ширины | `Container` |
| вертикальная композиция | `Stack` |
| горизонтальная композиция | `Group` |
| каталог | `SimpleGrid` |
| карточка товара | `Card` |
| пропорции изображения | `AspectRatio` |
| изображение | `Image` |
| статус | `Badge` |
| действие | `Button` |
| demo user | `Select` |
| первая загрузка | `Skeleton` |
| ошибка | `Alert` |
| пустое состояние | `EmptyState` |
| таймер / статус выполнения | `Progress`, `Text` |
| короткая обратная связь | `notifications` |

Собственные компоненты создаются для предметных элементов GoodQueue (`ProductCard`, экран очереди, состояние резерва), а не как замена существующим Mantine primitives.

Для проверки API компонентов использовать Mantine MCP, если он доступен. В остальных случаях использовать документацию `https://mantine.dev/llms.txt`.

## Responsive и accessibility

Интерфейс проектируется mobile-first, но desktop не должен выглядеть как растянутая мобильная версия.

Для адаптивности в первую очередь используются responsive props Mantine.

Интерактивные элементы должны оставаться доступными с клавиатуры. Действия реализуются через `Button`, навигация — через ссылки. Не используются кликабельные `div`.

Состояние нельзя обозначать только цветом.

## Что сознательно не реализуется

GoodQueue не пытается воспроизвести весь Avito.

Поиск, категории, избранное, корзина, продавцы, отзывы, чат, доставка, реклама, рассрочка, геолокация и другие элементы marketplace не добавляются, если они не участвуют непосредственно в демонстрации механики очереди.

Это позволяет сфокусировать MVP на бизнес-задаче: справедливо распределить ограниченный товар, понятно провести пользователя через ожидание и сохранить возможность продолжить покупку даже при негативном исходе.
