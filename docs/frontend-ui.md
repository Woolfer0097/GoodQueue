# Frontend UI/UX

Этот документ описывает реализованный интерфейс GoodQueue, а не план будущей разработки.
GoodQueue встраивает очередь на дефицитный товар в привычный покупательский сценарий
классифайд-платформы. Avito используется как референс информационной иерархии, но его
интерфейс и продуктовые возможности не копируются целиком.

Основная UI-библиотека проекта — Mantine 9. Для предметных элементов используются
собственные компоненты (`ProductCard`, действия покупки, экраны очереди), собранные из
Mantine primitives.

## UX-принципы

- Backend остаётся источником истины для наличия, очереди, резерва, сроков и результата
  покупки.
- Frontend валидирует ответы API, показывает подтверждённое состояние и не создаёт
  бизнес-переходы по локальному таймеру.
- Главное действие соответствует текущему состоянию товара и попытки выбранного
  demo-пользователя.
- Технические поля и ошибки переводятся в понятные пользовательские статусы и действия.
- Негативный результат не должен быть тупиком: где это уместно, пользователь может
  повторить попытку, вернуться в каталог или открыть альтернативу.

## Общая оболочка

Приложение использует минимальный `AppShell` без искусственной шапки классифайда. В правом
нижнем углу закреплены два demo-инструмента:

- переключатель светлой и тёмной темы;
- выбор активного demo-аккаунта через `Popover` и `Select`.

Выбор аккаунта относится только к демонстрации. UUID сохраняется в браузере, а данные
пользователя загружаются с backend. В production идентичность должна приходить из
доверенного auth-контекста.

## Каталог

Каталог отображается адаптивной сеткой: две колонки на mobile, три на небольшом desktop и
четыре на широком экране. Карточка содержит только полезные для сравнения данные:

- изображение или нейтральную заглушку;
- название;
- цену;
- краткий статус доступности.

Абсолютное число ожидающих в карточке не показывается: без позиции пользователя и ёмкости
очереди оно создаёт ложную точность. Карточка открывает страницу товара и не начинает
покупку напрямую.

При первой загрузке показываются skeleton-карточки. Уже загруженный каталог не скрывается
во время фонового обновления. Для пустого ответа используется `EmptyState`, для ошибки —
`Alert` с безопасным повтором запроса.

## Доступность и CTA

Frontend вычисляет только представление по данным товара, полученным от backend. Порядок
проверок важен:

| Данные API                                                         | Статус                      | Действие новой покупки |
| ------------------------------------------------------------------ | --------------------------- | ---------------------- |
| `queue_enabled = false`                                            | Покупка временно недоступна | disabled               |
| `allocatable_stock = 0`                                            | Нет в наличии               | disabled               |
| `free_stock > 0`                                                   | В наличии                   | `Купить`               |
| свободного товара нет и `waiting_count >= waiting_buffer_capacity` | Очередь заполнена           | disabled               |
| свободного товара нет, очередь принимает пользователей             | Доступно по очереди         | `Встать в очередь`     |

Проверка на клиенте улучшает UX, но не заменяет backend admission. Конкурентный ответ
`queue_full`, `queue_disabled` или `sold_out` всё равно обрабатывается как бизнес-результат,
а не как ошибка соединения.

## Страница товара

На desktop используется двухколоночная композиция: крупное изображение слева, цена,
название, доступность, категория, описание и действие справа. На узком экране блоки
выстраиваются вертикально.

Свободный остаток показывается только когда он положительный. Если доступна лишь очередь,
интерфейс сообщает, что свободных товаров сейчас нет. Внутренние поля `reserved`, UUID и
служебные коды пользователю не показываются.

Перед новой покупкой frontend загружает текущую попытку выбранного пользователя:

- активная попытка ведёт на её фактический этап;
- завершённая попытка объясняет результат и позволяет начать новую покупку, если текущая
  доступность это допускает;
- при ошибке проверки новая покупка блокируется до успешного повторного запроса.

Ниже основной информации отображаются похожие товары. Frontend сохраняет порядок backend,
не выбирает режим рекомендаций и не пересчитывает ranking.

## Очередь

Экран `waiting` показывает:

- подтверждение, что пользователь находится в очереди;
- место и общее число ожидающих, если эти поля пришли в API;
- прошедшее с создания попытки время;
- действие `Выйти из очереди`;
- доступные похожие товары.

Оценочное время ожидания и искусственный progress bar не показываются: backend не даёт
достоверный прогноз. Polling выполняется в фоне без повторного skeleton и без глобального
индикатора каждого запроса.

## Резерв и checkout

На экране `invited` пользователь видит, что товар сохранён за ним, обратный отсчёт и два
действия: перейти к оформлению или отказаться от резерва.

Checkout показывает товар, цену, оставшееся время и явное предупреждение о
демонстрационной оплате. Кнопка имитирует только успешный ответ платёжной системы; деньги не
списываются. Пользователь также может отказаться от покупки и освободить товар.

Countdown рассчитывается по серверному deadline только для отображения. При достижении нуля
frontend повторно запрашивает попытку, но не переводит её в expired самостоятельно.

## Финальные состояния

| Состояние          | Сообщение                | Основное продолжение                            |
| ------------------ | ------------------------ | ----------------------------------------------- |
| `purchased`        | Покупка завершена        | вернуться к товару и при доступности купить ещё |
| `cancelled`        | Покупка отменена         | вернуться к товару или в каталог                |
| `invite_expired`   | Время резерва истекло    | вернуться к товару                              |
| `checkout_expired` | Время оформления истекло | повторить покупку                               |
| `payment_failed`   | Оплата не прошла         | повторить покупку или выбрать другой товар      |
| `sold_out`         | Товар закончился         | вернуться в каталог или открыть альтернативу    |

Похожие товары отображаются для `cancelled`, `checkout_expired`, `payment_failed` и
`sold_out`. Для alternatives переиспользуется обычная `ProductCard`.

## Loading, ошибки и отсутствующие ресурсы

- Первая загрузка страницы отображается через `Skeleton`.
- Background refetch не заменяет уже загруженный контент skeleton-состоянием.
- Ошибка загрузки страницы показывается через `Alert`; результат отдельного действия — через
  notification.
- Запрос можно повторить только там, где повтор безопасен.
- `404 not_found` и `400 invalid_input` для некорректного product ID показывают единое
  состояние «Товар не найден» с возвратом в каталог.
- Неизвестный route использует отдельную минимальную 404-страницу.

## Responsive и accessibility

Интерфейс mobile-first, но desktop-композиции используют доступную ширину. Группы действий
разрешают перенос строк, поэтому кнопки не выходят за экран. Навигация реализована ссылками,
действия — кнопками; кликабельные `div` не используются. Статус всегда передаётся текстом, а
не только цветом. Loading, таймеры, списки и группы действий имеют доступные роли и подписи.

## Что не входит в frontend MVP

Frontend не реализует поиск, категории, избранное, корзину, продавцов, отзывы, чат,
доставку, рекламу, рассрочку или геолокацию. Также в SPA нет реальной платёжной формы,
списания денег, создания заказа, возвратов, WebSocket/SSE и push-уведомлений.

Frontend не обращается к внутреннему `/internal/v1/payment-events`: для демонстрации успеха
используется только публичный demo-payment endpoint.
